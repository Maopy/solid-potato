# 0.3.4 视频号发送回显与感谢恢复修复

修复真实日志中“消息已出现在公屏，程序却将发送判为未知，随后一直拦截感谢”的问题。本次不更改感谢文案池、价值分档、每用户 5 秒合并和随机 emoji。

## 修复内容

真实客户端的轮询响应使用 `baseResponse.Ret: 0`，旧实现只识别小写 `ret: 0`。现在兼容这两种字段；失败状态、字符串形式的零、缺失状态或两种字段相互矛盾时不作为有效回显。

点击发送后，输入框未及时清空仍会标记本地提交结果未知并暂停自动发送。在原有 12 秒回显观察窗口内，如果识别到同一动作的有效网络回显，会先将回显写入本地 SQLite，再记录 `echo_confirmed / network_echo_confirmed_no_resend`，检查该会话是否还有其他未解决的未知动作，最后确认是否解除暂停。页面只有收到该动作的本地恢复确认后才解除自己的发送暂停。该消息不会重新填入或再次点击发送。

回显必须符合原有约束：同一页面会话、完整文案一致、独立的原生消息 ID 和本地关联 ID、发送后的轮询请求；配置了发送账号时还需发送者一致。历史消息、其他用户、其他动作和其他房间的回显不能解除当前暂停。回显证据仍不代表所有观众都可见。

等待确认期间，新感谢保留在原有有限队列内，继续计算有效期。恢复后仅发送仍有效且满足输入框保护、暂停开关和账号限流的草稿；过期草稿不会补发。收到重复命令或重试回执不会重复发送或重复记录恢复。12 秒内没有足够证据时仍保持暂停，需要人工处理；不能据此判断原消息发送失败。

本版覆盖此前文档中“未知提交即使之后观察到回显也不自动恢复”的旧行为：现在只在上述条件满足、回显与恢复记录持久化成功后恢复。

## 更新

停止旧场控，替换 `live-archive-core`，保留自己的 YAML 和 data 目录。用原命令重新启动，关闭旧直播页后重新打开；脚本只在页面加载时注入，因此只替换程序但保留旧页面不会更新恢复逻辑。无需新增配置。

此前已卡住的历史感谢不会从旧数据库自动补发。更新后观察新礼物，诊断中的网络回显计数应增长；出现本地未知时，可检查 `fill_audits` 中的 `echo_confirmed` 记录，以及 `getStatus().fill.bridge.blocked` 是否恢复为 false。

## 验收

仅运行集成测试，使用本机 HTTP 服务、模拟页面和根据实际字段结构构造的匿名消息，不发送真实直播间消息。覆盖大小写响应状态、失败与冲突状态拒绝、9.5 秒延迟回显恢复、暂停期间保留草稿、恢复 ACK 丢失、重复旧回执不重新暂停、同一动作不重发、无回显保持暂停、跨房间凭证与恢复隔离，并回归原有两平台采集发送链路。
