# 0.2.6 本地日志自动清理

自动清理默认启用，原始采集保留 7 天，原始数据预算 2 GiB；感谢草稿、执行结果、规则预览以及筛选后的采集事件保留 30 天。时间以 UTC 入库时间为准，恰好位于保留期限边界的记录保留。旧 YAML 不填写清理配置也使用以下默认值。

```yaml
storage:
  raw_messages: true
  retention:
    enabled: true
    raw_days: 7
    raw_max_mib: 2048
    audit_days: 30
    preserved_runs: []
```

`raw_max_mib` 以 MiB 为单位，2048 MiB 即 2 GiB。程序按 Base64 数据长度加每分片 512 字节元数据预算估算原始记录占用；这是原始数据预算，不是整个 SQLite 文件、索引或 WAL 文件的精确物理上限。会先删除超过 7 天的原始记录，再按入库时间从最旧的完整消息开始删除，直至预算满足。整个 `capture_id` 的分片一起删除；仍在上传的未完成消息不会因为容量限制被拆开删除，但超过时间期限后可以整体删除。

启动代理前执行清理；正常运行时由已认证页面轮询每分钟检查一次，停止服务后再清理。因此运行中可能暂时超过预算。传输确认已经完成的分片即使被清理，之后的确认重试也不会让记录重新入库。

## 保留排查场次

将需要排查的启动场次 `run_id` 加到 `preserved_runs`，重新启动后生效。例如：

```yaml
storage:
  retention:
    preserved_runs:
      - '需要保留的实际 run_id'
```

程序停止时的汇总 JSON 和 `tools/read_moderation_raw.py` 查询结果包含 `run_id`。每次启动是独立场次，多个场次可以填多个 ID。同场次的原始消息、筛选事件、感谢草稿和执行结果都免于自动清理。移除 ID 后下次运行恢复正常策略。请在过期清理前加入保留列表，已清理的数据无法恢复。

保留场次与在途未完成消息也计入原始数据预算，但不会为了满足容量而删除它们。若仍超预算，固定清理日志会显示 `over_limit: true`，需要检查保留列表或调整容量。

## 空间回收与更新

删除记录后的数据库空页在运行中用于后续写入，不立即执行整库整理。启动前和停止服务后，空页至少 16 MiB、且占数据库页数至少 25% 时执行 `VACUUM` 回收空间，并尝试截断 WAL；运行中不执行整库整理。若有其他读取程序占用数据库，WAL 可能暂时无法完全截断。大数据库整理需要一些时间与临时磁盘空间。

关闭清理可设置 `storage.retention.enabled: false`。调整保留天数、容量和场次列表都需要重启。清理不改变礼物识别、感谢文案、自动填入或发送开关。

停止旧程序，用本包二进制替换旧程序，保留 `config/` 和 `data/`，再启动并刷新直播页面。默认策略会应用于已有数据库，无需清空旧数据。旧全量数据库首次启动会建立容量统计和时间索引，之后按增量维护，避免每分钟扫描消息正文。

集成测试验证时间边界、30 天审计保留、整条消息容量淘汰、保留场次超预算、在途分片、关闭清理、旧库迁移、实际文件收缩、HTTP 确认重试不恢复已淘汰消息，以及开启默认清理时的日志采集与感谢流程。没有向真实直播间发送测试消息。
