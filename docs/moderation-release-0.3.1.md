# 0.3.1 礼物采集完整性与发送回显

本版沿用 0.3.0 的多平台、多直播间控制入口。启动和任务配置见 `docs/moderation-release-0.3.0.md`。旧版 YAML 可以继续使用，自动发送仍由 `sending.automatic` 控制；本次更新不会主动开启发送。

## 礼物采集

- 视频号礼物候选取消原来每分钟 30 条的采样限制，与文字诊断的采样预算分开。同批最多检查 500 条，扩大了嵌套 JSON 和礼物载荷的解析范围。超过边界、解析失败或传输队列溢出会留下缺口诊断，原始采集仍按原有配置留存。
- 保留有效的 `combo_id`，按发送者、原生消息 ID 去重。同一消息明确出现同一礼物的计数增长时，作为续送活动重新等待 5 秒；计数回退、重复和展示字段修改不延长窗口。感谢仍不带数量。
- 20013 公屏展示消息单独记录为 `gift.summary`，重复展示去重，不触发新感谢。它与 20009 的发送者、礼物、接收目标和连击 ID 可用于核对；不能把公屏展示时间解释为送礼发生时间或连击结束时间。
- 原始日志、候选日志、感谢草稿的记录继续保留。这里的完整性指改进已到达页面的消息处理，不保证平台未推送、断线期间或未知协议的礼物能够补采。不同 20009 消息 ID 的尾条语义仍需更多真实样本，不能只凭数量相同去掉礼物。

## 发送确认

将本地提交结果和网络回显分别记录：

- `submitted`：点击发送后输入内容已清空，只表示本地提交。
- `echo_observed`：在 12 秒内观察到符合条件的网络消息回显，并关联到唯一的发送动作。
- `unconfirmed`：时限内没有足够证据，不能推断发送失败，也不会自动重发。

网络回显必须与完整文案一致，有独立消息 ID，且时间符合发送动作；相同消息不能确认多个动作，多个动作文案相同且无法区分时不确认。视频号只接受新的原生消息轮询回调，要求独立的 `client_msg_id` 与 `local_client_msg_id`。也支持实际桌面日志中的 `jsapi_resp.resp_json` 轮询结构。DOM 文字、清空输入框和普通发送回调不能单独作为回显证据。

抖音必须在房间 YAML 中配置**实际发送账号的用户 ID**，才能确认 WebSocket 中的回显；视频号可使用本地关联字段确认回显，也建议配置账号 ID 以进一步核对发送者：

```yaml
delivery:
  actor_user_id: '实际发送账号的用户ID'
```

这是平台消息中的完整 `user_id` / `username`，不是昵称、房间号或收礼目标 ID。数字 ID 需加引号；不能确认账号 ID 时保持不配置，抖音发送仍正常执行，但回显状态为未确认。配置需重启进程并重新打开直播页后生效。

视频号诊断面板新增“发送回显 / 待确认 / 未确认”计数；抖音可查看 `window.__liveArchiveModerationV1.getStatus().delivery_confirmation` 和 `[Live Archive delivery]` 日志。本地 SQLite 新增 `delivery_audits`，通过 `run_id + connection_id + action_id` 关联 `fill_audits`。回执丢失只重试本地入库，绝不重复点击发送。回显记录沿用审计日志的保留天数和保留运行策略。

网络回显证明当前采集通道看到了相应消息，不代表所有观众均可见，也不冒充官方送达回执。未知本地提交依旧暂停后续自动操作；即使随后看到回显，也不会自动解除暂停。

## 更新和验收

停止旧进程，替换 `live-archive-core`，保留自己的 YAML 和 data 目录。沿用原来的 `moderation run --config ...` 或 `moderation serve --config ...` 命令，关闭旧直播页后重新打开，加载新脚本。

本轮使用集成测试覆盖：80 条同批礼物、重复和 ACK 丢失、5 秒续送窗口、展示消息不重复感谢、抖音 protobuf 回显、视频号原生轮询回显、错误发送者/内容/本地回显拒绝、12 秒未确认、重复回执不重发、错误凭证/动作/页面拒绝、日志清理和多任务隔离。未运行单元测试，未向真实直播间发送测试文案；真实客户端的自然礼物回显仍需更新后现场复验。
