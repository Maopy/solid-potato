# 0.3.8 视频号回显识别与进场欢迎

修复一类“礼物草稿持续生成，但自动感谢停止”的问题。点击评论后，旧逻辑只接受点击后新发起的轮询返回的回显；如果平台已有轮询正在等待，点击前发起的请求也可能返回刚发送的消息。旧逻辑漏掉这条有效回显，遇到输入框未及时清空时把本条发送记为未确认，随后一直暂停自动发送。

现在在点击前保存已观察到的服务器消息序号；已有轮询返回后，只有消息序号严格更新、正文完全一致、用户和本地关联标记符合要求，才将它确认为网络回显。序号保持精确整数处理。没有序号基线、旧消息、错误账号、仅本地消息、失败的响应均不能解除暂停。仍先持久化本地结果及回显，再恢复后续新草稿；不重发已经点击的旧消息。

本次问题的本地采集显示：停止的那次点击约 1.1 秒后已有相同正文、同一发送者、不同服务器/本地消息 ID 的服务器回显，序号也晚于此前已观察到的聊天；旧程序仍把它记录为超时未确认。这个采集只能证明此类回显存在，不表示输入框状态或所有观众的送达状态均已验证。

## 同时包含的欢迎功能

普通进场按直播间收集 30 秒后合并欢迎，重复用户去重，过长名单自动缩短，无人进场时不生成消息。视频号“超粉”“星守护”按明确的原生徽章生成单独欢迎，每个用户每 60 秒最多一次，不重复加入普通名单。身份欢迎不是开通或升级通知。视频号徽章仍需现场验收；抖音这两类身份字段尚未接入。详见 [进场用户合并欢迎](moderation-welcome.md)。

```yaml
rules:
  welcome:
    enabled: true
  supporter_welcome:
    enabled: true
    template: '欢迎{title}{nickname}来到直播间，感谢支持！'
```

发布配置开启这两项欢迎；旧 YAML 中 `welcome.enabled: false` 会继续关闭普通欢迎。身份欢迎默认为开启，可以显式关闭 `supporter_welcome.enabled`。发送仍沿用原有手动填入或显式自动发送设置。

## 更新与验证

停止旧程序，替换为 0.3.8 的二进制后启动，可以继续通过 `--config` 使用原有 YAML 和数据目录。关闭旧直播页面并重新打开、开始采集，以加载修复后的注入代码。单纯重启旧版本不能获得修复。已有未确认发送不会补发，恢复后只处理新的礼物。

验证包括匿名化的跨点击轮询序号回放、错误账号/旧序号/缺失基线等拒绝场景，以及完整 SDK → HTTP → SQLite → 输入框的跨点击轮询回显恢复。验证恢复后的下一条感谢正常发送、前一条不重发、回执重试幂等。集成测试不连接真实直播平台。
