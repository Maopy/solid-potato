# 本地公屏留言评分

0.3.76 在中控每条公屏留言右侧显示 StartLux 的「关注分」，范围 0–100。
分数表示主播关注和回应的优先级，不是观众价值、违规概率或模型准确率。
主播语音不打分；留言顺序、采集、发送和场控开关均不受评分影响。

评分参考当前留言、之前 90 秒内最近三句主播语音和之前 30 秒内最近三条留言。
每条上下文均截取有限长度；没有语音时按留言内容判断。当前版本不回头重评主播后来才回答的问题。
五个等级分别为忽略、低、一般、高、紧急，官方 `score` 返回的零基期望等级乘以 25 后四舍五入显示。
这不是人工标注验证后的业务评分，中文直播效果还需要实际观察。

消息先显示，评分异步完成。等待显示「评分中」，队列满显示「待重试」，读取中控时会重试；
本地服务出错显示「评分异常」，不会伪装成 0 分，也不会阻止公屏继续展示。
两个房间使用同一个串行推理队列，但上下文、消息和评分各自隔离。
队列最多 128 条；直播极繁忙时评分可能滞后。所有评分随 30 分钟内存消息一起到期。

## 0.3.77：按需回复建议

中控每条公屏留言末尾的「回复建议」会请求三条话术：直接回应、互动追问、轻松接话。
StartLux 做候选选择，不自由生成文本。直接回应可选用主播最近原话；未知信息不补写。
上下文是点击时的目标留言、同房间最新 5 条其他留言、最新 5 句主播发言。
所以目标留言之后才出现的主播回答也可供参考；每段有长度上限，完整原文仍在时间线上。
没有主播语音时会显示「暂无主播发言，仅参考近期公屏」。

建议后台处理，不阻塞公屏。一次最多处理一个建议请求，可与留言评分并行。
同一条留言的待处理或已完成建议会复用；收起再展开不重复推理。
建议缓存随 30 分钟消息一起到期，不持久化、不自动发送；用户可复制后自行编辑。
全程本地推理，不调用云端生成接口。当前基于有限话术库，表达变化和复杂问题覆盖有局限。

## 0.3.78：本条留言优先

入口改为绿色 AI 图标。模型第一步只根据目标留言判断其意图，第二个判断从近 5 条公屏和近 5 句主播发言
中选择最多一条能直接回答或澄清目标的辅助信息，无关内容不进入最终回复选择。
问候和夸赞的话术库独立于上下文，避免被附近的歌曲、舞蹈等话题带偏。
本条留言使用完整文本；上下文只作参考。界面显示「针对本条留言 · 上下文仅供参考」。

## 本机安装位置

本次本机已安装：

- 模型：`dist/.live-archive-models/StartLux-Decision-v1.1-0.8B-Instant`
- 官方推理源码、独立 Python 依赖：`dist/.live-archive-tools/StartLux-Decision`、`startlux-venv`
- 本机服务启动器：`dist/.live-archive-tools/startlux_service.py`
- 服务配置：`dist/.live-archive-tools/startlux-runtime.json`
- 中控连接配置：`dist/decision.dev.json`
- 诊断日志：`dist/.live-archive-tools/startlux.log`，默认不记录留言正文。

中控在可执行文件所在目录及上三级目录查找 `decision.dev.json`；也可通过
`LIVE_ARCHIVE_DECISION_CONFIG` 指定配置路径。配置中只有本机接口、密钥文件和启动器路径。
API 密钥不发到网页，也不包含在 ZIP 中。只连接 `127.0.0.1`，不使用系统网络代理。
服务尚未运行时，第一条留言会自动启动本地模型；同机多次启动只保留一个服务。
服务在场控关闭后仍驻留，以便下次复用；可通过本地任务管理器停止对应的 StartLux Python 进程。

此机器使用 RTX 3090、BF16、官方 Transformers 后端（5.8.1）、双向提示词注意力。
Windows 下启用相同计算的数学 SDPA 路径，最大上下文 2048，保留官方全部注意力自检。
语音识别环境不升级；独立 StartLux 环境复用已安装的 CUDA PyTorch 2.10.0。

## 0.4.32 评分调整

评分更重视结合话题的观点、解读和有讨论价值的短句；常规活动文案、场控引导与重复模板优先级降低。明确的短促引导关注或灯牌文案最高 25 分；包含问题或较长的混合内容交由模型判断。模型可能仍会误判，评分仅供参考，不改变消息顺序或自动执行操作。

## 0.4.32：本地生成回复

回复建议由单独安装的 Qwen3-4B-Instruct-2507 生成，不再从固定句库挑选。模型读取目标留言和点击时同房间最近的主播发言、公屏和先后顺序，尝试给出最多三条内容不同的回复。上下文不足以判断时可能只给一条澄清。生成内容不自动发送，使用前需要核对；生成模型仍可能误解上下文或产生不准确的内容。

该历史版本当时使用单独安装的 Qwen3 模型，运行需要至少 11 GB 空闲显存；此方案已在 0.4.35 按用户要求移除，当前版本不再依赖该模型。

## 0.4.35：恢复候选话术

按用户要求移除 Qwen 生成模型的使用，回复建议恢复为 StartLux 从固定话术中挑选。话术覆盖有限，复杂留言可能不够具体；不会自动发送。

## 0.4.36：原模型的定向优化

继续使用已有 StartLux 决策模型，从候选话术中选择建议。针对提及酒楼、饭店等餐饮大客户的经营讨论增加采购、供货和渠道方面的候选；明确投诉仍走原有分类。缺少参考信息时，“有几个”等无法确定指代的短留言只显示一条澄清。其余场景仍依赖有限的候选话术，不保证对所有话题都能给出具体建议。

## 0.5.4：染发留言的话题上下文

对“不要染”等简短留言，若目标前 60 秒至后 8 秒内的同房间主播发言提供了染发或漂发颜色线索，就从相关发色话术中选择，并去除同义建议。衣物染色等冲突线索或没有可信上下文时，提示澄清，不猜测主播发色。此规则只覆盖有限场景，其他话题仍依赖现有话术。

## 0.5.5：具体事件的即时反应

评分提示增加对具体动作、事件的简短即时反应的识别，例如“倒立开合跳，玩这么大”。模型根据留言和已有上下文评估，不以这些词作为固定加分规则；上下文不足、语音转写延迟时仍可能误判。评分不会在后续语音出现后自动重算。

## 0.5.8 评分标准

本地模型区分正常沟通、恶意人身攻击、场控宣传和其他无意义消息。正常沟通至少 60 分，恶意人身攻击最高 20 分，宣传及其他类别最高 55 分。正常批评和不同意见按正常沟通处理。分类可能误判，评分仅供参考。

## 0.5.12 重复低分文案

同一直播间内两分钟内完全相同（忽略首尾空白）的低分留言，复用最近一次成功评分；正常沟通、不同内容及评分失败不复用。误判可能随重复留言延续。
