## 后续修复顺序

1. **录制停止时尾段损坏（实际复现）**：`src/recorder.rs` 在停止分支直接调用 `child.kill()`，可能中断视频包写入。最后一个分段报 `error while decoding MB 28 86, bytestream -6`，但会话仍记录正常结束。优先让 FFmpeg 有机会正常收尾，并增加实际 FFmpeg 停止录制的验证。
2. **桌面错误和状态消息不可见（实际复现）**：空链接点击保存后无可见提示。`Dashboard.message` 存放校验及进程错误，`render` 未渲染该字段，保存失败或启动失败时用户也难以判断原因。
3. **GUI 与 CLI 默认任务库不同（代码确认）**：CLI 用 `tasks.sqlite3`，GUI 用 `live-archive.sqlite3`；GUI 子进程显式传入 GUI 数据库，所以 GUI 内部录制可以共享，但直接执行默认 CLI 命令看不到 GUI 的同一份任务。统一路径时需要考虑已有两份数据的迁移。
4. **GUI 子进程退出后无法可靠重启（代码风险，尚未实测）**：`recordings` 保存 Child，但刷新逻辑没有 `try_wait` 或退出清理；`start_douyin` 遇到已存 ID 直接返回。录制自行结束或失败后可能出现按钮可点却不重新启动的问题。
5. **开发版 GUI 依赖启动目录（代码风险，尚未实测录制）**：`core_command` 调用 `cargo run`，没有指定工作目录或 manifest。从项目目录外打开 debug GUI 时，可能找不到 Cargo.toml。当前桌面测试使用临时 .app 包装已编译程序，仅检查交互，未通过此包装启动录制。
6. **文档过时**：README 仍称抖音 resolver 未配置，并把已存在的解析、代理捕获和桌面壳列为后续增量；应根据真实能力更新说明及 GUI 启动命令。

## 当天后续：核心停止录制修复

已修复 `src/recorder.rs` 的停止流程：保留独立的 FFmpeg stdin 控制管道，发送 `q` 后等待正常退出，再转封装 MP4。控制管道必须从 Child 中单独取出，否则 Tokio 的 `Child::wait` 在首次等待时会提前关闭 stdin，导致退出指令失效。

退出等待上限为 10 秒。无响应时仍会终止并回收进程、尽可能转封装已写出的文件，但返回明确错误，提示尾段可能不完整；正常退出失败也不再当作干净收尾。增加了取消时自动终止子进程、忽略 false 停止通知、处理已发出的停止请求和关闭控制通道等保护。

同时修复 `src/service.rs`：单次录制和持续监控在停止期间发生收尾错误时，都会向调用方返回错误，保留失败历史，不再通过重试循环吞掉错误并返回成功。停止状态和停止句柄清理仍正常完成。
