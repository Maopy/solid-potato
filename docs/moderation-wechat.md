# 视频号桌面客户端注入

0.2.0 新增 `candidate_fill_only`：在明确核对接收目标后自动填入不带数量的感谢，由用户手动发送。正式使用步骤见 [0.2.0 使用说明](moderation-release-0.2.0.md)。下文保留观察模式的协议边界。

目标是微信桌面客户端内的视频号直播页面，复用录屏使用的 mitmproxy 同源响应注入方式。此次没有使用 Playwright，也没有开发官方助手自动化或 UI。

## 当前能力与边界

已打通独立 YAML 配置 → 代理注入 bootstrap → SDK 配对 → 受认证本地 HTTP 桥接 → SQLite 日志。探针被动观察当前页面原本发起的 fetch、XHR、WebSocket；如果页面已有录屏的 `WXE` 事件总线，还会监听直播资料和进入直播事件。它不会调用平台 API、建立额外平台连接或发送消息。

只记录通信渠道、文本/二进制类型、消息长度、回调类别和字段层级/类型，例如 `$.data.giftList:array`。常见协议字段保留名称，未知及动态键使用 `unknown_序号`，不输出原键名。观察范围为当前页面自己发起的 HTTPS/WSS 微信和腾讯域名通信（`weixin.qq.com`、`qq.com`、`weixinbridge.com` 及其子域名），不再仅匹配 HTML 所在域名；本地场控桥接排除在采集之外。新增域名不会扩大代理解密范围，只由页面脚本观察。域名、路径和查询参数不输出。

诊断事件不记录完整响应、业务内容、昵称、用户 ID、直播 ID、Cookie、URL 查询参数或原始网络帧。结构样本不包含字段值；消息批次诊断只保留有界整数类型码及计数。新增文字候选事件单独保留限定文字及来源标识，边界如下。基础诊断每分钟最多输出 60 条；单次结构最多访问 200 项、深度 7、每对象 50 个键、24 个字段（路径最长 64 字符），每页最多 100 种去重结构。访问器只标注为 `accessor`，不执行 getter。原生回调检查前 3 个参数，用 `$.args[0]` 等标明位置；空值、普通字符串等也有类型样本，不再必须命中已知消息字段。字符串内对象/数组 JSON 标记为 `<json>`，每次最多解析 3 段、合计 64 KiB，不执行或解码其他文本。类别为 `invoke_callback`、`call_callback`、`dispatch` 或 `dispatch_json`，不输出动态接口名或事件名值。原生调用额外保留固定枚举 `api_kind`：`message`、`gift`、`room`、`media`、`cgi`、`other`；它来自本地接口名称提示，只用于定位通信，不代表已解码对应互动事件。安全字段白名单覆盖常见协议封装、消息、礼物字段及确定的大小写、下划线变体，未知键仍按位置匿名化。回调参数数组和 JSON 编码层不消耗业务对象的深度预算。fetch 文本读取上限 64 KiB、最多并发 4 个读取、2 秒取消；XHR 文本同样限长，二进制暂不解码。停止后还原采集钩子并移除探针监听；已注册原生 on 回调的身份兼容垫片例外，见下文。

`probe.message_batch` 对结构扫描遇到的 `msg_list` 做批次统计：最多检查前 50 项、最多 8 种类型；仅接受 0–65535 的整数 `type`，其他值归为未知。记录总数（最多 10000）、检查数、截断标志、超出类型预算数，以及各类型的文字 / JSON / 不透明 / 缺失内容计数。内容只在页面本地判断格式，最多解析 8 KiB 的对象/数组 JSON，不保存内容或标识值；不执行 getter。扫描仍受深度 7、200 项、每对象 50 个键和 JSON 解析总预算约束，字段展示上限不提前终止批次发现。多次轮询可能重复返回同一条消息，所以批次数和已检查条目数不是去重互动数，也不是礼物数量。暂停后不继续检查或增长统计，诊断仍受每分钟输出限额约束。

`probe.message_match` 增加页面内文字对照。只将非 JSON、2–1024 字符的内容短暂放入本地内存，最多 32 个候选，8 秒对照窗口（下次 1 秒定时检查后移除）。有候选时每秒最多扫描 400 个文本节点、32 KiB 文字或 10 毫秒，排除诊断面板、输入框、脚本和样式，检查节点所在元素的尺寸、可视区域及显示样式。暂停和停止立即清空候选；导航异常也清理过期候选。控制端仅留存类型码、命中/未命中计数、检查数、窗口和扫描受限标志，不留存候选内容或 DOM 文字。

命中只是页面可见文字与消息文本的包含匹配，可能是历史文字或页面其他标签，不证明它是弹幕；未命中也可能由延迟、扫描预算、分割 DOM、画布或其他上下文造成。因此不得据此自动认定事件类型或触发场控规则，重复候选也不算唯一消息。

### 文字消息候选

仅从当前页面原生桥接的 `msg_list` 处理整数类型 1，生成独立的 `chat.candidate`。这是基于真实页面对照证据的候选解码，不是已确认的 `chat.received`。事件包含最多 256 个 Unicode 字符的内容、截断标志、来源 `client_msg_id` / `username` / 可选昵称，以及固定候选解码器标记。内容输入上限 8 KiB，空内容和合法对象/数组 JSON 不生成文字候选；`[强]` 等普通文字不按 JSON 丢弃。标识必须来自消息自身，非空、最长 128 个 Unicode 字符且没有控制字符，不编造标识。缺少标识、字段访问器及异常字段仅计为候选跳过。其他类型维持诊断。

去重键为当前文档中的发送者与消息 ID。缓存最多 2048 项，暂停保留、停止清空；超出后移除最早一项，移出的旧消息再次出现可能重新生成候选。因此候选计数不代表永久去重数量。同 ID 同内容仅增加重复计数，同 ID 不同内容仅增加冲突计数，比较原始内容以识别截断位置之后的差异；同内容不同 ID、不同发送者同 ID 仍分别生成候选。

候选每分钟最多输出 30 条，独立于诊断每分钟 60 条的额度；SDK 缓冲已满或候选额度用完时，不写入去重缓存，后续重复轮询仍有重试机会。生成数表示 SDK 接受的事件数；“确认入库”仅在本地桥接返回有效序号 ACK 后增加，“未确认”为两者差值。ACK 丢失时使用同一序号重试，确认计数不会翻倍。页面关闭、缓冲丢弃或代理异常中断不保证补发，采集暂停期间的消息也不保证回补。

所有候选固定 `live_eligible=false`、`room_verified=false`、`confidence=candidate`；后端也强制这些状态，页面提供的标志不能升级权限。独立事件类型不接入现有场控规则，微信模式仍只允许 observe，集成测试验证没有预览或填入动作。日志现在会包含候选聊天文字和来源消息/用户标识，仍不保存完整网络响应或凭证。

**尚未验证视频号真实互动消息格式和直播间身份，故不支持规则预览、感谢或输入框填入。** YAML 的 `rules_preview`、`scheduler_preview`、`fill_only` 会在启动前被拒绝。`/web/pages/live` 只是页面路由，同一路由可能展示不同直播间，不能拿它当稳定房间 ID。

## 本机验收

```sh
cp moderation.wechat.example.yml moderation.wechat.yml
cargo run -p live-archive-core -- moderation check --config moderation.wechat.yml
cargo run -p live-archive-core -- moderation run --config moderation.wechat.yml
```

1. 先停止占用同一端口的抖音探针或录屏代理；本版尚未把两个 sidecar 合并为共享进程，不要同时竞争端口。默认监听 `127.0.0.1:2024`，可通过 YAML 修改。
2. 示例已启用 `injection.system_proxy: true`。启动命令会复用录屏流程：先启动代理，再检查本地 CA 信任并按需安装，保存当前 HTTP/HTTPS 代理后设置到本地端口。接受系统需要的权限提示，无需去微信里单独配置代理。若使用之前复制的 YAML，请补上这个字段。
3. 关闭并重新打开一个正在直播的视频号页面，确保 HTML 请求重新经过代理。客户端可能缓存页面；没有 bootstrap 请求时先排查路由、代理和缓存，不表示规则失效。
4. 直播页面右侧应出现「场控诊断」按钮，位于现有录制按钮下方。点击展开面板，连接成功后点击「开始采集」。无需开发者工具；注入后默认不采集直播通信，需按钮启动。
5. 面板显示连接状态、通信消息数、结构样本数、已忽略数，以及最近 10 项渠道和字段类型。等待实际直播通信，观察数字是否增长；显示字段名不表示礼物已解码。点击「暂停采集」停止新增诊断，再点「开始采集」可继续；暂停时保持桥接和钩子，避免错过继续采集时的已有 WebSocket。
6. 再点击「场控诊断」收起面板，只收起显示，不暂停采集。关闭页面会移除入口、监听和钩子；Ctrl-C 停止本地服务并恢复原 HTTP/HTTPS 代理。若连接异常，面板会提示检查本地场控服务。没有入口则先排查 HTML 注入、页面缓存和实际路由。

`system_proxy` 默认为 false，仅视频号桌面适配允许启用，设置为 true 表示允许本次运行设置系统代理和处理本地 CA。抖音仍采用之前的浏览器代理方式。代理只解密选定的平台页面域名，媒体 CDN 及其他域名透传。正常结束、Ctrl-C、代理异常退出及启动失败会尝试恢复代理，失败会报错并保留原快照供进程清理重试；强制杀进程或断电无法保证自动恢复。CA 与录屏流程一致，停止后保留信任配置。

如需在另一个终端查看已存储诊断，也可使用下面命令。不要把整份数据库或客户端凭据发到聊天中。

```sh
sqlite3 data/moderation-wechat/moderation-probe.sqlite3 \
  "SELECT json_extract(event_json,'$.payload') FROM probe_events WHERE json_extract(event_json,'$.event_type')='probe.schema' ORDER BY rowid DESC LIMIT 20;"
```

`connected` 只说明注入和桥接正常，诊断里出现 `gift` 字段也不等于礼物计数已正确解码。若观察数一直为零，客户端可能使用原生通信、其他域名、Worker/iframe 上下文或其他页面路由；面板会提示这一边界，发现页面替换 fetch/XHR/WebSocket 钩子时会提示采集可能不完整。当前入口仍严格限制到 `channels.weixin.qq.com/web/pages/live`，不能宣称已覆盖客户端全部通信。

点击「开始采集」（包括暂停后继续）时，会检查并重新包装页面当前的 fetch、XHR.open 和 WebSocket，保留页面实现的参数、返回值和构造行为。页面自己的包装若仍调用旧探针，响应、XHR 和 socket 监听会去重，避免一次消息重复计数；停止 SDK 时恢复页面当前实现。采集期间不会定时覆盖页面钩子：若页面稍后再次替换它们，可暂停再开始重新挂载。重新挂载只覆盖之后经过这些入口的通信，不能接管已经存在且从未被探针观察的 socket；普通网络钩子也不能覆盖原生或 Worker 通信。公屏新增文字本身不计入网络消息数。

探针也会在页面已有 `WeixinJSBridge` 对象上，被动包装实际存在且可写的 `invoke`、`call` 回调和 `_handleMessageFromWeixin` / `_handleMessageFromWeixinJSON` 入口。不调用桥接 API，不主动订阅，不改变请求参数、原生返回值或页面回调的参数和 `this`；仅在采集中记录回调数据类型和允许的字段结构。SDK 停止时恢复仍由本探针持有的属性。面板的「原生监听入口」表示当前对象实际挂载的函数数，0 说明这些入口未暴露或不可写；大于 0 也不保证互动经过这些入口。原生结构以 `native_bridge` 渠道单独标记，不把它当作已解码礼物。页面直接渲染的公屏、其他桥接、Worker 和 iframe 仍可能不经过这些入口。

代理在请求/响应头阶段启用流式转发，仅选定页面 HTML 和本地桥接保留缓冲；API、事件流及媒体响应不等待完整正文再发送，避免持续响应被代理缓存拖延。媒体 CDN 及其他域名仍保持 TLS 透传。机制见 [mitmproxy 流式转发文档](https://docs.mitmproxy.org/stable/overview/features/#streaming)。桌面探针桥接轮询间隔为 2 秒；相同诊断阶段仅记录一次，面板内容仅在状态变化时重绘。

## 页面一直 loading 的对比诊断

先 Ctrl-C 停止注入模式，确认直连恢复播放。运行纯转发诊断：

```sh
cargo run -p live-archive-core -- moderation run --config moderation.wechat.passthrough.example.yml
```

该配置启用系统代理，但 `injection.tls_passthrough: true` 让 HTTPS 原样转发，不解密、不注入按钮，也不检查或安装 CA。机制参考 [mitmproxy 域名透传说明](https://docs.mitmproxy.org/stable/howto-ignoredomains/)。重新打开直播，测试后 Ctrl-C 恢复代理。

纯转发仍 loading：问题发生在代理转发、上游网络或客户端使用代理的阶段，需要先解决这层。纯转发正常、注入模式 loading：故障更可能发生在 HTTPS 解密、客户端证书校验或注入阶段，尚不能仅凭这一对比认定证书固定。

### 注入成功但微信或播放卡顿

先停止普通场控，重新关闭并打开直播页面，恢复正常观看；暂停采集不会停止代理，也不会移除已安装的网络钩子，不能作为排除代理或脚本影响的对照。

如果纯转发正常、普通注入模式卡顿，用仅 TLS 解密模式把两者分开：

```sh
cargo run -p live-archive-core -- moderation run --config moderation.wechat.tls-only.example.yml
```

重新关闭并打开直播页面，不能复用仍包含旧脚本的页面。此模式使用正常模式相同的 CA 和选择性域名解密，但 HTML 完全不改写、不插入按钮或脚本、不发起页面桥接轮询，也不清除原缓存验证头。示例最多运行 60 秒后恢复原代理，遇到卡顿可以提前 Ctrl-C。

- 仅解密模式仍卡：脚本不是卡顿的必要条件，接下来排查该域名解密、协议或微信的代理兼容性。
- 仅解密模式流畅：接下来排查注入脚本、网络钩子、桥接和页面兼容性。

`injection.tls_only` 与 `tls_passthrough` 都是仅视频号支持的诊断选项，不能同时为 true。诊断模式没有按钮是预期行为；一次本地代理流式测试通过不代表真实微信已恢复流畅。

如果仅解密仍卡，可在其他条件不变时关闭 HTTP/2 进行协议对比：

```sh
cargo run -p live-archive-core -- moderation run --config moderation.wechat.http1.example.yml
```

该配置仍不注入代码，最多运行 60 秒。唯一新增变量是 `injection.http2: false`，代理对被解密的连接使用 HTTP/1；保持 TLS 透传的连接不改变原协议。默认配置依然启用 HTTP/2，正式模式不因未验证的假设改变。选项含义见 [mitmproxy 官方选项说明](https://docs.mitmproxy.org/stable/concepts/options/)。若关闭 HTTP/2 后流畅，再将这个设置用于普通注入模式验收；若仍卡，不能认定 HTTP/2 是原因，继续检查连接失败、上游状态与解密兼容性。

终端会记录选定平台上游实际 HTTP/1.1 或 HTTP/2 协议，以及 4xx/5xx 错误类别，每种仅一次，不输出请求地址、头或正文。HTTP/1 对比时请一并保留这些固定诊断行。

仅解密模式每 10 秒输出 `transport summary` 数字汇总：请求数、收到响应头及完成数、响应字节数、最大响应头等待毫秒数、超过 2 秒的响应头数，以及 TLS/HTTP 失败数。流式计数原样返回每段字节，不缓存正文。范围仅为选定解密域名，未包含透传的媒体 CDN；请求尚未收到响应头时不计入最大等待，长连接尚未完成也不代表失败。没有新连接或只有少量请求的汇总，不能用于认定卡顿已解决。

注入模式终端会输出最多 40 条固定诊断文字，同一阶段不重复刷屏，区分平台 CONNECT、客户端/上游 TLS 失败、平台 HTTP 失败、页面收到及注入插入、bootstrap 服务成功或失败。不记录 URL 参数、错误对象、请求头、Cookie 或响应正文。出现 loading 时，请提供这些固定诊断行即可。

如果出现 `platform client TLS failed`，故障发生在微信与代理的 TLS 握手，尚未进入页面注入。新日志还会把错误归为 `certificate rejected`、`protocol mismatch`、`connection closed` 或 `unclassified`，只输出固定类别，不输出原始错误。证书拒绝本身不能证明证书固定，也可能是当前 CA 未受客户端信任。

macOS 检测会先核对钥匙串里完整公共证书是否与当前场控目录的 CA 一致，再评估信任。仅有另一个同名 `mitmproxy` 证书或 CA 叶证书的基本校验成功，不能跳过当前 CA 安装。安装时明确读取当前用户默认钥匙串，通过 `-k` 指定目标，并设置 SSL/basic 信任；安装命令完成后再次核对当前 CA，失败则在设置代理之前终止启动，不会仅凭安装命令退出成功就继续运行。此检查仍不能证明微信使用系统的信任结果。

如果升级后提示证书安装，请完成系统信任提示，随后彻底退出并重新打开微信，再测试普通注入配置。如果仍有客户端 TLS 失败，保留诊断类别继续排查；纯转发只能恢复观看，不能提供场控按钮。mitmproxy 的 [macOS 证书安装说明](https://docs.mitmproxy.org/stable/concepts/certificates/) 也明确指定了目标钥匙串；其系统钥匙串安装方法需要管理员权限，本项目默认保持当前用户范围。

## 自动化集成测试

自动化使用完整注入脚本、模拟客户端和 DOM 环境及真实本地 HTTP 服务，验证延迟挂载入口、点击展开、启动/暂停/继续采集、面板诊断、配对、fetch/XHR/WebSocket/已有事件总线观测、字段值不外传、SQLite 留存、错误来源拒绝和停止还原。它不连接真实视频号、不发送，也不能代替实际微信版本的页面布局及注入验收。

真实代理流式集成测试（需安装 mitmdump）会启动本地媒体/事件持续响应及独立临时代理，验证服务端尚未结束响应时客户端已收到第一段数据，随后验证完整尾段。它不修改系统代理或钥匙串，也不连接平台：

```sh
python3 tests/moderation_streaming_integration.py
```

下一阶段根据本机验收得到的通信结构确认可靠事件来源、稳定用户/房间/消息标识和礼物数量语义，再接统一规则核心。无法确认的事件保持 diagnostic，不生成欢迎或感谢动作。

### 正常退出与缓存确认

Ctrl-C 或限时结束时，控制端先进入排空状态，拒绝新页面配对和 bootstrap，保留既有认证会话和代理最多 8 秒。页面收到停止通知后暂停采集，立即逐批提交现有缓存；每批最多 50 条，只有入库 ACK 才移出缓存并增加确认计数。所有缓存已确认后发送 goodbye，恢复原页面钩子并停止 SDK。此期间控制端不规划新动作，也不下发填入命令。

如果页面无响应、后台定时器暂停、网络失败或 ACK 未到，8 秒窗口结束后仍会恢复代理并退出；终端明确显示排空未完成，再次 Ctrl-C 可提前结束等待。现有 HTTP 请求自身有 3 秒截止，退出时允许它们完成响应，再关闭代理进程。强制杀进程、页面关闭和系统异常仍不能保证缓存完整入库。“sessions closed”只表示已连接会话结束，不保证此前页面关闭时丢弃的数据已回补。

### 礼物字段与命令载荷诊断

`probe.gift_schema` 独立保留包含明确 gift / gift_info / gift_id / gift_name / gift_count 等已知字段的名称和类型。结构先保留根字段，再按广度优先检查子对象、数组和嵌套 JSON 字符串，最多 24 个字段；每个对象最多 20 个键、数组最多 3 项，仅遍历深度不超过 3 的对象，最多 100 个节点。嵌套字符串最多解析 3 段、每段 8 KiB、合计 16 KiB，不执行访问器。会扫描普通封装、消息 content 的对象/数组 JSON，以及命令响应中的 JSON。页面最多 32 种结构；礼物线索聚焦扫描最多深度 4、100 个节点（含嵌套字符串）、每数组 3 项。每批消息最多聚焦检查 8 个 JSON 内容。动态键仍按位置匿名化，字段值不输出。字段存在也可能来自礼物目录或配置，不表示发生了送礼。

`probe.command` 仅检查原生桥接中的整数 `cmd_id`（0–65535），每对象前 20 个键、最多 8 个字符串，每字符串最多 8 KiB、合计 32 KiB。只输出命令码、格式计数及结构；区分对象/数组 JSON、严格字符集的 Base64 候选、普通文字和超长字符串。Base64 只在本地解码；Protobuf 只验证并记录顶层字段编号与 varint / fixed64 / bytes / fixed32 类型，不输出标量值或字节内容，最多 100 个标签、12 个结构字段。截断、错误长度、非法字段号、未知 wire type、超长 varint 均不能成为有效候选。语法有效也不说明它属于哪个平台事件，Base64 候选也可能是普通编码文本。

命令、应用载荷、礼物结构线索共享独立每分钟 30 条额度，避免高频轮询占满既有诊断额度；原有诊断每分钟 60 条、文字候选每分钟 30 条仍独立限制。命令诊断按完整安全结构去重、页面最多保留 32 种；面板命令响应次数仍统计每次观察。上述诊断，不扩大代理解密域名、不调用新平台接口、不解析执行代码，结构线索本身不生成 `gift.observed`，也不计算连击增量、累计数量或触发感谢。已核对字段的 20009 reward 载荷可以生成独立 `gift.candidate`，具体条件见下文；候选仍不能进入感谢规则。

### 20009 应用载荷线索

公开参考源码：[wordweb/Get-Tencent-Video-Live-Barrage-Gifts 的 webapi.py](https://github.com/wordweb/Get-Tencent-Video-Live-Barrage-Gifts/blob/main/webapi.py)。其中主播助手接口的 `appMsgList` / `msgType=20009` / `payload` 使用 Base64 → UTF-8 → JSON 的解析路径。该来源不是微信官方协议，也不证明桌面观看页格式相同；本项目没有采用它的登录或主动接口轮询流程。

探针仅在已收到的原生对象中观察 `msg_type` 或 `msgType` 为 20009 的条目，`payload` 最多 8 KiB，尝试普通对象/数组 JSON 或严格 Base64 + 有效 UTF-8 JSON。非法编码保持 opaque，不猜测类型。`probe.application` 只输出类型、格式、最多 24 个安全结构字段及礼物字段线索数量（使用上述有界嵌套结构检查），每页最多 32 种去重诊断结构；不输出 Base64、解码文字或标识。礼物相关结构另记为 `probe.gift_schema`，仍不是礼物事件。命令字符串同样支持 Base64 JSON 格式诊断，并与 Protobuf 候选区分。

命令 JSON 聚焦扫描还会尝试最多 3 段嵌套对象/数组 JSON 字符串，每段最多 8 KiB、合计 16 KiB，并观察其中的 20009 应用条目；不递归主动调用平台接口。解码后的命令 JSON 只保留根层最多 12 个安全字段及类型，方便确认真实封装，仍不输出正文。

### 原生 on 事件回调观察

补充包装页面自身调用 `WeixinJSBridge.on(name, callback)` 时的回调，诊断类别为 `on_callback`。只在已有可写函数上包装，不自行注册订阅、调用平台 API、修改事件名或注销页面监听。回调 this、所有参数、返回值和异常行为保留；同一桥接/事件名/原函数复用包装身份，最多 1000 个映射。off 使用原回调时透明翻译为对应包装函数。若已有 off 不可写、不是自身函数属性或无法包装，则不包装 on。

停止采集时不观察回调。SDK 停止后，对已发生包装注册的桥接保留有界 on/off 身份垫片，继续只转发页面自己的注册和注销，所有数据观察已关闭；不能简单还原 off，因为原生注册表仍持有包装后的回调。其他采集钩子照常还原。垫片仅属于当前文档，不保证页面任意重写桥接实现后的行为；重新加载文档会清除它。

注册在探针包装前的回调不会追溯观察，因此真实验证需要刷新直播页，并在页面自身建立订阅后采样。面板列出的原生入口名称来自固定白名单，不能据入口存在就认定已收到礼物。


### 应用消息列表与外层身份结构

通用结构探针仅采样数组前三项；对原生 `app_msg_list` / `appMsgList` 专门检查前 50 项，并对本次原生封装的已处理对象去重。多个已知应用列表共享 50 项扫描预算，最多处理 50 个 20009 对象，不表示覆盖所有消息或跨轮询去重。不会将应用列表之外的任意数组当作消息源。

`probe.application.envelope_fields` 额外保留原生条目的有界字段结构，采用同一 24 字段、深度和匿名键规则。有限白名单增加 `fromUserContact`、`finderLiveContact` 和 `contact` 及已有协议变体；诊断中不保留消息 ID、用户 ID、昵称或 payload 原文。外层字段诊断本身不生成礼物候选；reward 候选要求真实消息和发送者标识，数量语义仍保持未知。

若解码后的 20009 对象自身包含普通 `content` 文字，会在页面本地按既有 8 秒窗口做文字包含对照，记录为 `probe.message_match` 的类型 20009，仅输出命中数量。匹配可能来自其他标签或提示，未匹配可能来自扫描限制；两者均不能独立证明送礼、奖励、单次数量或连击累计。


### 页面本地字段核对

诊断面板新增“本地字段核对”，默认关闭。手动打开后，只检查随后收到的 20009 解码对象，在当前文档内保留最多 3 个摘要，关闭或 SDK 停止清空。显示原生条目及解码根层的短字段名/类型，以及第一个含 name 的直接子对象结构；每层最多 20 个键，最多 60 个标签。只有 48 字符内的 ASCII 属性标签可原样显示，其他标签匿名化，wxid/长十六进制标签仍匿名化；这是开发核对入口，不是严格白名单诊断。

可显示该直接子对象的 name（最多 64 个字符），以及命名为 count/quantity/num/repeat/combo 的非负整数（最多 100 万），不显示其他字段值、消息正文、Base64、身份值或访问器返回值。名称尚不能单独证明是收到的礼物，数值也不自动成为增量或累计数量。摘要不放入 SDK decoder 状态，不经事件桥接、不写 SQLite；入库的字段仍使用原有有限词汇白名单。字段名与数值的关联必须在真实客户端核对后才能写入解码器。


### 视频号 reward 礼物候选 v1

真实客户端本地核对确认：20009 解码根包含 `reward_product_id`、`reward_gift.name`、`reward_product_count`、`combo_product_count`，外层包含 `client_msg_id` 和 `from_user_contact`。实际“小星星”样本的两个计数均为 66；这没有证明计数是单次增量或连击累计，也没有确认所有 20009 都属于送礼。候选实现以真实字段拼写为依据，仍不认定 `gift.observed`。

`gift.candidate` 只接受原生 20009 的对象 JSON 或 Base64 UTF-8 JSON 根对象中的明确 reward 结构，要求 `client_msg_id`、`from_user_contact.contact.username`、`reward_product_id` 为合法非空字符串；`reward_gift.name` 非空、原值最多 1024 字符，显示最多 64 个 Unicode 字符并标记截断。消息/发送者/礼物 ID 均不生成替代值。`reward_product_count` 必须为 1–100 万的安全整数，`combo_product_count` 可缺失，存在时必须为 0–100 万的安全整数，不能默认补 1。

事件仅保留观察到的公开消息/发送者标识、昵称、礼物 ID/名称及原始两个计数，不保留整个条目、原始 payload、任意字段或其他身份值。数量模式强制为 `unknown`，没有规范化 quantity、增量、连击组 ID 或结束标志。`confidence=candidate`、`live_eligible=false`、`room_verified=false` 同时由前端和服务端强制；不进入规则引擎，不生成感谢/填入动作。面板独立显示礼物候选生成、确认入库、重复、冲突、跳过和限额计数。

当前文档内以发送者 + 来源消息 ID 去重，最多 2048 项，先进先出淘汰；重复内容只计重复，同 ID 的礼物名/礼物 ID/两个计数发生变化则记录冲突并跳过。此变化可能是合法连击修订，需要更多证据才能按修订处理。暂停保留缓存，SDK 停止清空；跨页面/重启不共享缓存，当前未验证房间切换。每分钟独立 30 条，SDK 接受事件后才写去重缓存，限额或缓冲拒绝仍可在后续观察重试。原诊断 60、结构线索 30、文字候选 30、礼物候选 30 分别限额，合计最多 150 条/分钟。

真实核对验证了字段拼写和本地视图；新增候选解码/去重/ACK/服务端清洗通过完整 SDK→HTTP→SQLite 集成测试，尚未完成新候选版本的真实直播入库验收。后续需对照同一用户同一礼物的连续消息，确认稳定连击标识、数量变化及接收者/直播身份后，才能建立增量或累计映射并接入 5 秒感谢规则。


### 只读礼物计数检查

```sh
cargo run -p live-archive-core -- moderation inspect-gifts --journal data/moderation-wechat/moderation-probe.sqlite3
```

默认检查日志最新一次 run；即使该 run 没有礼物，也不回退到旧直播。可用 `--run-id` 指定已有 run，`--limit` 控制读取最后多少条候选，默认 2000、范围 1–10000。只读打开已有 SQLite，不建立或迁移表、不打开录制数据库、不启动代理、不调用规则引擎。报告生成于一个只读快照，按入库顺序检查候选；无法反映所有平台事件、丢弃或未入库数据。

按当前 run 的连接文档、发送者和礼物 ID 分组，输出匿名 group / document 编号和原始两个计数字段的变化；不输出 run ID、连接 ID、消息 ID、用户 ID、昵称、礼物名称/ID或其他载荷。组不等于连击组，无法从两个相邻候选推定它们属于同一次连击。重复消息 ID/相同内容与冲突分别统计，不再次累计；不同文档分别处理。只接收本版本微信 reward 候选，身份无效、数量超界、标记不符合或其他解码器均计入 rejected_rows。

每组保留最多 32 个最近样本，最多输出 50 组，明确给出输入/样本截断和 omitted_groups；统计计数仍覆盖已扫描的有效样本。matching_count_rises 只表示相邻 combo 字段上涨的差值恰好等于当前 reward 字段，其他上涨和非上涨分别统计，不是数量语义验证。没有总赠送量、没有计算有效增量，报告 quantity_mode 永远 unknown、live_eligible 永远 false。

礼物候选额外保留原生条目的 `is_floatmsg`、`float_type` 数值线索，仅接受 0–65535 的整数，缺失/不支持时不补值。报告缺失显示 null，不能把 null 当作 0 或把某个类型值自动解释为连击结束。它们不参与消息 ID/礼物计数去重指纹；只显示已有候选的来源线索，尚不支持同 ID 的类型变更修订。

完整 CLI→临时 journal 集成测试验证匿名输出、类型与数量边界、重复/冲突、文档隔离、最新 run 空数据不回退、明确指定 run、读取/输出限制、只读文件字节不变，以及不存在的文件不创建。


### PK 来源目标隔离与归零模式

礼物候选从原生条目 `to_user_contact.contact.username` 读取可选来源目标；仅保留合法非空标识为 `recipient_user_id`，缺失/非法不补值。它不证明该目标就是当前主播，也不证明多目标列表的完整接收者，room_verified / live_eligible 仍为 false。同一发送者/消息 ID 的来源目标改变视为冲突，保留最初已接受候选，不按同一赠送盲目合并或修改。

inspect-gifts 增加来源目标维度，已知不同目标分别分组，未知目标单独分组，不与已知目标关联。recipient 只输出文档内目标的匿名编号（编号在本次报告内分配），缺失为 null；不显示原始目标标识。历史缺少目标的候选仍可报告，但其组可能混合多个未识别目标，不能用于确认连击语义。

每个样本额外显示 receipt_gap_ms，为同组相邻唯一候选在 SQLite 的入库时间差，非平台送礼发生时间。无法解析时间或缺少前项时为 null，时钟回拨可能为负；批量入库、轮询、后台暂停都可能影响此间隔，不能据此确认结束时刻。

count_pattern 仅标记数值关系：combo_missing、positive_combo、zero_matching_previous_total（当前 combo 为 0，当前 reward 等于上一候选的正 combo）、zero_other。组中分别统计两种归零模式，所有原始候选保留为唯一消息，不据模式删除、不计算有效赠送量，不认定结束或补发。多个独立连击、漏采和不同源类型均可出现同样数值关系；需要稳定连击身份和真实类型语义证据再用于去重/规则。


### 同消息 ID 的修订观测

原实现仅累计同 ID 的冲突并跳过，无法复查消息数量变化。现在已接受的 gift.candidate 若再次观察到同一发送者/消息 ID，而礼物 ID/名称、两个计数、目标或类型标记发生变化，会生成独立 gift.candidate_revision；相同修订状态只留存一次，最多 2048 个去重键。原始候选的去重基线保留，不把修订当作新增 gift.candidate，不生成 gift.observed 或感谢。

修订可保留当前计数为 0 的消息，但必须已有该消息 ID 的初始正数量候选；没有上下文的独立 0 数量消息仍跳过。记录当前字段及初始候选的 previous_reward_product_count、可选 previous_combo_product_count / previous_recipient_user_id / previous_is_floatmsg / previous_float_type，reason 固定 same_message_changed。previous_* 始终指最初接受的候选，非上一条修订，也不证明变更就是结束。没有保留载荷原文或访问其他身份字段。

修订和普通礼物候选共享每分钟 30 条额度；SDK 接受后才记修订去重，拒绝时可重试。暂停保留两个有界缓存，SDK 停止清空。重复状态可因缓存淘汰再次出现。服务端对两种类型均强制 candidate、unknown、room_unverified、ineligible；数量模式不能通过页面自报标记变成可执行。

inspect-gifts 同时读取这两种类型。普通候选仍进入原有 group 统计，修订单独输出 revisions / revision_rows，不增加 unique_messages 或组内 messages，也不从总量中加/减。source_message 为本报告内的匿名来源消息编号，可关联原始样本与修订；prior_message_seen 表示原始候选是否在本次读取范围，缺少时计 unmatched_revisions。

since_first_candidate_ms 是修订入库时间与初始候选入库时间的差；读到的历史被截断、时间无效或缺少初始候选时为 null。它不是平台事件间隔，时钟变化可使结果为负。修订样本最多保留最近 50 条并标记截断；修订的当前/先前目标仅输出匿名编号，不显示原始标识或名称。此记录用于核对复用 ID 的结束消息，不据它自动删除事件或确认数量语义。

   ```sh
   cargo run -p live-archive-core -- moderation inspect-gift-targets --journal data/moderation-wechat/moderation-probe.sqlite3
   ```

   只读取最新一次运行，最多扫描最近 10000 条候选；输出接收目标的原始 `recipient_user_id` 和候选条数，不输出送礼用户、文案、礼物名。与匿名 `inspect-gifts` 命令不同，这个命令专用于本地手动选择目标，不宜直接分享输出。若最新运行没有候选，不回退旧运行。目标条数用于辅助观察，不代表礼物数量或主播身份。

2. 复制示例 YAML 为自己的配置，并填写**已明确确认属于当前主播**的来源目标：

   ```yaml
   mode: observe
   candidate_preview:
     enabled: true
     recipient_user_id: '明确选定的来源目标 ID'
   ```

   无法确定目标时保持 `enabled: false`。系统不会猜测 PK 中哪个目标是当前主播。更换主播或直播时停止程序、重新采集并确认目标；配置需重启生效。缺少目标、非视频号平台、TLS 纯转发/仅解密配置会校验失败。原有 rules_preview / scheduler_preview / fill_only 禁用限制不变。

3. 启动自己的配置，在诊断面板点击“开始采集”。无需发消息或送礼。匹配目标的唯一候选按页面连接与用户分别聚合，自最后一条新候选被控制端接收起等待 5 秒。SDK 轮询时检查期限，因此日志会有轮询间隔的延迟；这不是平台送礼时刻。

   文案：`感谢昵称送来的小星星、鲜花`。名称按首次出现顺序去重，不拼数量。礼物名称合计超过 30 个 Unicode 字符（不计分隔符），或来源名称已截断时，文案为完整的 `感谢礼物飘屏`。缺少昵称用“这位观众”。终端以 `live-archive moderation: candidate draft` 输出，并落入独立表 `candidate_draft_audits`，带 `live_eligible=false`、`room_verified=false`、`fill_input=false`、`send_chat=false`。它是候选文案，不证明礼物实际发生或数量。

重复候选、ACK 重试、修订不会延后期限。目标缺失/不同、非明确解码候选不参与。若待处理消息的修订改成其他目标，则丢弃该用户当前窗口；其他修订只作采集证据，不生成新感谢。暂停采集、观测缺口、连接失效或页面关闭丢弃待处理窗口；停止程序不强制提前感谢。每连接最多 500 个待处理用户、10000 个去重 ID（每用户窗口另限 100 条），达到边界时停止接收超限候选，不逐出旧 ID 导致重复感谢。

此阶段只测试日志和落库，不填聊天输入框、不发送。真实尾条语义仍未确认，独立 ID 的尾条仍可能被当作候选，所以此能力不接入自动执行。

本地字段核对开启后，20009 条目若含 `to_user_contact.contact.username` 与 `nickname`，显示“来源目标（未验证）”名称及 ID，便于与当前页面主播核对。仅显示最近三个载荷中的最新样本，名称最多 64 字、ID 最多 128 字；开关关闭或脚本停止即清除。不写入 SDK 状态、HTTP 或 SQLite。名称可能重名或缺失，单凭名称不验证接收者/房间；无法明确对应时不要启用候选感谢预览。

### 预览状态与来源关联

启用 YAML `candidate_preview` 并重启后，场控诊断的正常视图显示配置目标（仍未验证）、待感谢用户总数、最多 10 位用户的剩余等待时间、累计生成数、过滤/取消计数和最近草稿。关闭“本地字段核对”可回到完整诊断视图。倒计时基于控制端轮询快照，在页面内递减；归零不表示文案已经生成，须等待后续确认。桥接失败或停止后显示状态已过期，不能拿旧倒计时判断当前窗口。

`window.__liveArchiveModerationV1.getStatus().candidate_preview` 返回同样的只读诊断信息。`pending_truncated=true` 表示仅展示部分待处理用户；`recent` 最多保留 5 条草稿/取消记录，因此不是完整历史。过滤计数按候选消息累计，取消计数按用户窗口累计，来源仅覆盖已观测的消息。过滤原因包含目标缺失、其他目标、候选无效、重复、仅修订、暂停期间、去重/用户上限；取消原因包含暂停、观测缺口、目标变更、窗口上限、页面关闭/变化、连接失效及服务停止。重复 ACK 不重复增加计数。

完整历史仍在独立 SQLite 的 `candidate_draft_audits`：`kind=gift_candidate_draft` 是生成文案，`kind=gift_candidate_cancelled` 是取消窗口，不能把后者算成感谢。两类都包含 `source_messages`，每项有原事件 `seq`、`event_id` 和 `native_event_id`，可通过该表的 `run_id` / `connection_id` 与 `probe_events` 精确关联。草稿另带控制端单调时钟的 `last_candidate_at_ms`、`due_at_ms`、`at_ms`，期限与最后接收相差 5000ms。这些不是平台送礼时间，亦不是 UTC 时间戳。轮询响应只包含最近记录摘要，不反复传输完整来源列表；完整来源只在本地日志里保留。

每个用户窗口最多关联 100 条候选；超过时取消窗口并记 `window_limit`，避免单条诊断/日志无限膨胀。暂停后控制端拒绝继续聚合，收到“开始采集”状态才恢复；已处理消息 ID 在暂停恢复间继续去重。连接连续 30 秒未通过认证请求续期时取消旧窗口，新页面连接单独计数和聚合。停止只取消未完成窗口，不提前生成感谢。

查看本轮生成与取消记录时，可使用 SQLite 只读查询（数据库路径按 YAML 调整）：

```sh
sqlite3 -readonly data/moderation-wechat/moderation-probe.sqlite3 \
  "SELECT received_at, json_extract(audit_json,'$.kind'), json_extract(audit_json,'$.reason'), json_extract(audit_json,'$.text') FROM candidate_draft_audits ORDER BY id DESC LIMIT 20;"
```

其中 `reason` 仅取消记录有值，`text` 仅文案记录有值。日志包含有界的观察身份/昵称/礼物文案，核对用，分享前应匿名化。所有状态与记录仍为 `send_chat=false`、`fill_input=false`、`live_eligible=false`，不进入填入/发送执行链。

取消由具体采集事件触发时，另有 `trigger_event`，关联导致取消的暂停/缺口/目标修订或超限消息；来源列表保留被取消窗口原有的礼物候选。服务停止、连接超时、goodbye 等生命周期取消没有伪造的触发消息 ID。

### 入场语义核对（尚不触发欢迎）

新增 `probe.message_content`，当前只对真实观察到但语义未解释的原生 `msg_list.type=10005` 做诊断。其他类型仍走原有批次探针，不自动归类成入场。它识别缺失、普通文本、JSON、严格 Base64/UTF-8 JSON、不透明内容，保留最多 8 个内容字段、6 个原生条目字段的类型；不保留文本、昵称或任何身份值。显示 `sender_id_present` / `message_id_present` / `nickname_present` 与嵌套 `finder_live_contact.contact` 的身份字段是否存在，且不把两种身份位置自动当作同一个用户。

`content_empty` 仅说明原 content 字符串是否为空白，不能推断事件语义。`arrival_text_hint` 仅是有界文本以“来了”或“进入直播间”结尾的布尔线索；即使为 true，也不能证明入场或当前直播间归属。后端始终清除事件身份值，强制 `confidence=unknown`、`room_verified=false`、`live_eligible=false`。不会生成 member.candidate / member.entered、不会规划欢迎草稿。

探针最多保存每页面 32 种结构签名，独立每分钟 30 条诊断，共用 SDK 有界缓存，避免挤占礼物/命令诊断额度。签名只含格式、字段类型与布尔值，不使用原文或身份作为去重键。当前最大采集预算在原 150 条/分钟基础上增加该探针最多 30 条/分钟；非全部都一定实际产生。暂停或停止不观察，脚本退出清理签名。

诊断按钮和预览状态现置于面板上方，采集开关不需滚动即可使用。真实字段核对还缺少入场语义、身份字段对应关系与房间归属的确认，所以欢迎预览暂未启用。后续应依据明确样本注册独立事件解码器，避免用消息类型编号或普通聊天里的“来了”直接触发欢迎。
