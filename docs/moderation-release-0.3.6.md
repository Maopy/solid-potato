# 0.3.6 定时随机发送文案

新增抖音、视频号房间级的定时文案，支持配置多条并随机抽取。与礼物感谢共用现有输入框、发送队列、账号限流、发送回显和未知结果恢复机制，不需要新注入入口。

## 配置

在现有房间 YAML 顶层配置以下内容；已有同名节点时修改原节点，不要重复追加：

```yaml
sending:
  automatic: true

timed_messages:
  enabled: true
  interval_seconds: 300
  messages:
    - '新来的朋友欢迎呀，喜欢直播可以点个关注✨'
    - '精彩继续，喜欢就一起聊起来🎉'
    - '感谢大家的陪伴，欢迎常来玩💖'
```

`interval_seconds` 是发送检查间隔，默认 300 秒，支持 1–86400 秒；不是整点或某个钟点的计划。每次从列表随机选择，至少两条时避开上一条选中的文案，只有一条时会重复。按原文发送，不插入昵称、不套礼物模板，也不自动追加礼物 emoji；可以直接在文案中写 emoji。每条非空、不得含换行或两端空白，不得重复，最多 64 条，每条不超过 `limits.max_text_chars` 且最多 80 个 Unicode 字符。

默认配置中本功能关闭。需要 `sending.automatic: true`，并使用现有自动发送模式：抖音 `fill_only`，视频号 `candidate_fill_only`，不能与 `fill_test_text` 或 TLS 诊断模式混用。它共用现有自动发送开关，当前不能在“礼物只填入”的运行模式里单独自动发送定时文案。

`config/timed-messages.example.yml` 是可复制的配置片段，不能单独启动。修改后重启场控、关闭旧直播页再重新打开；不需要改昵称表或感谢文案池。

## 运行规则

- 页面连接后等待完整间隔再检查；视频号从点击“开始采集”后计时，未开始采集时不发送。即使没有礼物，也能独立运行。
- 礼物的 5 秒合并窗口、待发送感谢和其他待处理互动优先。定时文案只在队列空闲、输入框可用、发送未暂停且账号预算允许时下发；已经下发的消息不会被新礼物撤回。
- 输入框有手写草稿、礼物正在合并、账号限流、发送结果未知等忙碌情况，跳过这一轮并重新等待一个间隔，不积攒多条补发。视频号输入框收起时，会在临近发送检查时尝试用现有入口展开，仍不会覆盖手写草稿。
- 暂停采集时停止计时，恢复后等待完整间隔；收到直播结束或采集缺口信号时停止本次计时。重新打开页面或重新绑定任务会创建新计时，不补发断开期间的消息。退出场控时不会补发。
- 文案只选择一次，写入日志后按同一动作 ID 执行，命令或回执重试不会重新抽取、再次填入或重复点击。没有回显不能推断失败，沿用 0.3.4 的未知结果暂停与恢复规则。

实际间隔同时受页面轮询和账号预算影响。即使配置 1 秒，也不会绕过每账号默认最短 8 秒、每分钟最多 6 条的发送限制。多个房间各自配置、各自选文案；同一配置账号共用发送预算，不同账号独立。

## 诊断

`window.__liveArchiveModerationV1.getStatus().timed_messages` 可查看 `enabled`、`active`、`remaining_ms`、`generated` 和 `skipped`。generated 表示已经选中并尝试入队的文案次数，不是送达次数；skipped 表示忙碌等原因跳过的轮次。

数据库继续使用 `fill_audits` 与 `delivery_audits`，动作 ID 以 `timed-` 开头。queued 记录包含选定文案，后续 issued、submitted、unknown、echo_confirmed 和回显证据沿用同一个 ID，保留策略不变。

## 更新与验收

停止旧场控、替换 `live-archive-core`，保留自己的 YAML、昵称表和数据目录。新包的房间配置含关闭的示例，需要手动开启后才发送。

仅运行本机集成测试，不发送真实直播间消息。验证两平台无礼物时的完整定时发送链路、随机不连续重复、微信收起输入框自动展开、回执丢失不重发、开始/暂停/恢复、礼物优先、手写输入保护、未知结果暂停、忙碌不积压、房间独立文案、共享账号限流和非法配置预检；同时回归现有礼物、昵称映射与回显恢复。
