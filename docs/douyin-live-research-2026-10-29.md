# 抖音直播状态与录制链路调研

调研日期：2026-10-29。第三方项目为 [Douyin_TikTok_Download_API](https://github.com/Evil0ctal/Douyin_TikTok_Download_API)，检查时 main 指向 `b5505e3830a2e4b9b8608962f58e96dfe75f23c5`。本次未安装或运行第三方服务，也未接入第三方代码。

## 现有能力

- `src/douyin.rs` 的 `DouyinWebLookup` 使用用户保存在系统凭据库中的会话请求房间页面，从响应文本提取 HLS/FLV 地址。它不生成签名；缺少地址目前返回 `Offline`，HTTP 404 也返回 `Offline`。
- `src/service.rs` 的 `monitor` 区分 `Offline` 的固定间隔轮询与其他错误的退避重试，找到流后调用录制器；这是录制核心能力，不代表场控页面已提供添加房间并自动开录的完整操作。
- 场控录制当前依赖已打开并播放的直播页面，用户点击录制；任务只在当前运行内保留。参见 `docs/moderation-recording.md`。

## 小范围网络探测

使用项目已有测试房间 `139244611014` 和配置中的 `992927935592`，以当前解析器所用 User-Agent、不带登录凭据发起一次 HTTPS 页面请求；只记录状态、响应大小和是否匹配当前流地址正则，不保存页面或流地址。两次都返回 HTTP 200，页面分别约 933607、935284 字符，均未匹配到 HLS/FLV 地址。

这是未登录、各一次的观察，未通过直播页面或第三方接口独立核对当时是否开播，也未测试已授权会话、流可播放性或持续稳定性。结果不能证明房间未开播，也不能证明第三方方案有效。HTTP 200 且未发现流地址可能来自未开播、登录限制或页面结构变化等多种原因，现有解析器将其一律归为未开播会隐藏不确定性。

## 第三方能力与集成判断

第三方 README 列出抖音直播间状态、拉流地址和批量状态查询；其服务依赖独立身份池和调度机制，提供 REST 接口。该说明是项目自述，尚未对本机、目标房间或已授权会话实测。它不是视频号的解决方案；其身份、签名机制也不应在未经验证的情况下直接纳入当前桌面程序。

## 建议验证步骤

1. 在用户授权的会话下，选至少一个确认正在直播和一个确认未直播的房间，分别对照页面、当前解析器与自部署第三方接口的结果；不要在日志或报告中保存 Cookie、完整流地址或签名参数。
2. 对开播房间验证返回地址确实可播放，并观察一段时间及直播结束、重新开播后的变化。一次成功不足以证明长期可靠。
3. 设计诊断状态时将“明确未开播”和“未取得流地址，原因未知”分开；只有基于已验证的状态字段才判定未开播。网络、认证及录制进程错误分别呈现，并避免向界面暴露凭据或签名。
4. 明确需要的用户操作和开播监测生命周期，再决定是否将核心轮询接入场控。优先沿用已授权会话和现有架构，避免把外部演示站作为生产依赖。

本次没有修改产品功能、版本号或发布包；真实会话对照与端到端验证仍待完成。
