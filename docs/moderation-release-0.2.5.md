# 0.2.5 开发阶段全量消息日志

使用 YAML 启动时，默认将注入脚本收到的直播消息写入本地 SQLite 的 `raw_messages` 表。保存发生在消息识别、语义去重、目标过滤及候选采集限额之前。重复回调也保存为独立记录；传输重试按分片序号幂等入库，不会重复保存同一次采集。

```yaml
storage:
  directory: ../data/wechat
  raw_messages: true
```

原有 YAML 省略 `raw_messages` 也默认启用；设为 `false` 可关闭。旧 `moderation probe` 参数入口保持原行为，开发采集请使用 `moderation run --config ...`。

覆盖视频号的已挂接原生桥接入站回调、相关 WebSocket、JSON/文本 HTTP 响应及直播资料事件；视频号仍需点击“开始采集”。抖音记录相关 WebSocket 原始帧及 JSON/文本 HTTP 响应，二进制帧以 Base64 保存。未知消息类型、未识别礼物、其他收礼目标及重复数据都保留。记录范围是注入脚本能收到的消息，不是微信全部网络流量；不包含未挂接通道、启动采集之前的历史消息或视频/音频流。原始数据仅用于排查，不作为发送依据。

不记录请求头或 Cookie 请求信息；JSON 中已知的 Cookie、认证 Token、密码等字段脱敏，JSON 字符串与 Base64 包装的 JSON 也会处理。用户标识、昵称、直播消息及未知业务字段会存于本机。不是网络抓包的逐字节副本，已知认证字段会替换为 `[REDACTED]`。

原始日志有独立上传队列和序号，不占用候选礼物限额或感谢队列。每个记录按 24 KiB 分片，经入库提交才确认。取消之前的 32 MiB 数据库上限，开发日志不会按数量或时间自动清理，需要自行管理磁盘空间。

为了保护页面，仍有资源边界：原始队列约 8 MiB；单条 Base64 数据最多 4 MiB，二进制/HTTP 响应最多 3 MiB；JSON 遍历最多 200000 节点、128 层。溢出、循环对象、读响应超时等会产生明确的 `gap` 记录，而不是悄悄当作完整采集。诊断面板显示采集数、待入库分片、丢失数与上传错误。退出页面/断开网络/关闭进程时未确认的数据可能丢失；Ctrl-C 会尝试排空队列，异常退出或超出排空窗口不保证完整保存。未完整入库的分片也会在读取工具中标记。

## 查询

同一数据库中，`probe_events` 仍是筛选后的识别结果，`candidate_draft_audits` 是感谢草稿，`fill_audits` 是执行结果，新增的 `raw_messages` 是原始采集。每次启动有独立 `run_id`；一个完整消息由同连接的 `capture_id`、`part`、`parts` 重组。`captured_at_ms` 是页面采集时间，`received_at` 是入库时间。

在解压目录运行以下命令（需要 Python 3），可只读查询最新一次采集、重组分片并恢复 JSON：

```sh
python3 tools/read_moderation_raw.py data/wechat/moderation-probe.sqlite3 --contains '陌' --limit 10
```

省略 `--contains` 查看最新记录；`--run` 指定历史启动记录。原始日志可能包含公开聊天内容与用户标识，分享排查片段前按需要删去无关信息。

## 更新与验证

Ctrl-C 停止原程序，用本包的 `live-archive-core` 替换旧程序，保留原 `config/`、`data/`，重新运行并刷新直播页，再点击开始采集。不要覆盖原收礼目标或证书配置。新增查询工具可以单独复制。无需开启自动发送即可采集原始日志；原有感谢策略和发送开关继续使用原配置。

本版通过本机集成测试覆盖未知消息、超过采样范围的批次、重复回调、候选限额、二进制帧、大消息分片、确认响应丢失后的重传、认证/来源校验、脱敏、明确缺口，以及开启原始采集时的既有感谢填入/提交流程。本次未向真实直播间发送测试消息。更新前的缺失消息无法补录。
