# 智能场控方案评估

日期：2026-10-12。此文只评估架构及验证路径，不启动 UI 或功能开发。

后续用户已确定当前版本采用抖音注入、视频号注入与官方助手页面自动化；核心支持未来平台扩展。以[当前版本架构](smart-moderation-architecture.md)为实施依据，下方官方能力与四种模式内容保留为调研记录，官方接入不属于当前版本。

## 已确认的需求

- 在抖音和视频号直播间自动发送文字，感谢礼物、欢迎观众、祝贺升级。
- 视频号同时支持浏览器页面与微信电脑客户端的直播窗口。
- 升级包括粉丝团等级和用户荣誉/财富等级；各平台的等级含义及可见字段必须分别验证，不能直接视为相同。
- 页面脚本采集事件、执行有限操作；本地控制端决定行为，双方双向通信。

## 判断

架构方向可行，适合把 Rust 核心扩展为统一场控服务，录制作为独立能力保留。主要未知项不是 Rust 与脚本通信，而是各客户端能否稳定提供事件、当前登录身份能否发送文字，以及能否确认平台实际接受消息。

目前不能承诺两平台、两种视频号客户端都能获得完整礼物/入场/升级事件。首先在主播或授权场控账号实际使用的页面做能力验证；现有观众侧录制页面不能替代主播后台验证。

## 现有代码的复用边界

- `src/wechat_inject.rs`、`src/capture_sidecar.rs`：已有视频号页面资源注入和代理转发，可借鉴初始化与页面观察机制。
- `src/wechat_bridge.rs`：已有 Rust→页面请求→对应响应的 WebSocket 模式，但请求内容是录制所需的直播信息，不是场控事件或发送文字。
- `src/download_task_bridge.rs`：已有状态推送模式。
- Tokio、SQLite、系统凭据库和核心录制服务可继续使用；场控状态、队列及日志应独立建模，不混入录制任务状态。

现有 `ChannelsBridge` 只保存一个 sender，新连接会覆盖旧连接，任一连接断开又会清空 sender；握手未校验 Origin 或配对身份，使用无界队列，超时请求的 pending 项没有清理。它不适合直接承担多房间主动发言控制，应新建专用通信模块。

## 接入路线

| 环境 | 建议 | 待验证项 |
| --- | --- | --- |
| 抖音浏览器 | 浏览器扩展承载页面适配器；根据账号资格评估官方数据接入 | 事件完整性、发送身份和发送确认 |
| 视频号浏览器 | 优先扩展；现有代理注入作为实验适配路线 | 实际管理页的事件字段、输入框行为、登录切换 |
| 微信电脑客户端 | 独立的嵌入页面/原生窗口适配器验证 | 是否存在可注入网页、页面加载链路及消息控件是否可访问 |

Chrome 内容脚本默认与页面 JS 隔离，访问页面内部对象需要明确安排 MAIN world 桥接；页面可以干扰 MAIN world 脚本。扩展不能直接注入微信客户端。扩展到本地 Rust 推荐 `content script → service worker → Native Messaging → Rust`，消息和来源需要校验。[Chrome 内容脚本文档](https://developer.chrome.com/docs/extensions/develop/concepts/content-scripts)、[Native Messaging 文档](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)。

项目现有 HTTPS 代理注入依赖页面确实经过代理、信任本地证书且响应可修改，不能据此推断任意微信版本和窗口都支持。若客户端能力验证失败，浏览器版仍可独立交付，客户端版单列适配工作。

抖音官方直播伴侣互动工具文档包含评论、礼物、点赞、关注及粉丝团变更，并带荣誉/粉丝团等级字段；这些字段不代表每次等级提升都有独立事件，也不代表获得全部入场事件或文字发送接口。该指南的 Demo 是 Windows C++ 路线，不能直接套用为当前 macOS 项目的通用接入。[开发者指南](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/development/tutorial/live-tool-guide)。

后续核实补充：粉丝团变更已有明确原因字段 `fansclub_reason_type`（1 升级、2 加团、16 退团），可据此识别粉丝团升级；荣誉等级字段 `user_privilege_level` 则不能据此保证存在独立升级事件。详见文末官方能力复核。

查询时官方互动工具接入页标注“插件业务更新中，暂不准入新插件”。直播小玩法是另一条有申请和应用场景限制的能力路线，其 FAQ 明确不开放全量或指定用户评论。故官方方案需先验证资格和能力范围，不能假设通用自动场控可直接接入。[互动工具接入指南](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/introduction/interactive-tools-guide)、[直播玩法 FAQ](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/introduction/zn/FAQ)。

本轮没有找到足以确认视频号通用场控事件及文字发送能力的公开官方文档，暂列未知；这不等于断言平台不存在相关合作接口。自动发言和页面注入的长期可用性、账号限制及平台允许范围需另行核验。

## 控制端与脚本职责

页面脚本负责识别平台/账号/房间、报告支持能力、提取实际可见事件、执行预定义 `send_chat` 操作并返回结果。不放规则决策和模型密钥，不接受任意 JS、任意 URL 请求或系统命令。

Rust 负责事件归一化、去重、用户状态、连击礼物合并、规则匹配、生成文字、限流队列、执行许可、房间路由和审计。AI 用于有需要的话术改写或后续问答；感谢、欢迎和升级检测先采用确定规则，模型超时回退模板。

```text
平台事件 → 页面/客户端适配器 → 本地事件归一化
                                 ↓
                      去重、用户状态与礼物合并
                                 ↓
                         规则引擎、可选 AI
                                 ↓
                        限流、有期限的动作队列
                                 ↓
                    指定房间执行器 → 文字发送结果
```

## 关键协议约定

事件包含 `version / platform / room_id / room_session / source_id / event_id / occurred_at / observed_at / user_id / type / payload`。平台原始 ID 优先用于去重；缺少 ID 时标记为推断事件，不承诺全局严格去重。用户按平台标识，不使用昵称作为唯一身份。

动作包含 `action_id / room_session / executor_id / type / text / expires_at`。收到命令、写入输入框、提交平台和平台确认是不同状态；确认不了时返回 `unknown`，不要盲目重发，以免重复感谢。平台未提供幂等发送能力时，不能保证消息严格只发送一次。

- 按账号和房间授权，控制端与执行端都校验当前房间会话；换房、刷新和登录切换使旧动作失效。
- 同一房间同时打开浏览器和微信客户端时，只选一个有效发送执行器；采集源可多个，执行权限单一。
- 断线后先恢复连接和当前会话，再决定未过期动作是否执行；欢迎消息不补发积压的历史欢迎。
- 心跳、消息大小上限、有界队列、来源校验和短期配对凭据是主动控制协议的基础；回环监听本身不能证明来源可信。
- 直播间评论与昵称都作为数据处理；不把观众文字当模型工具指令，不允许其扩展动作范围。

## 各功能的难点

| 功能 | 必须处理的情况 |
| --- | --- |
| 礼物感谢 | 连击数量可能累计上报；按连击标识计算增量或等待结束，避免 1、2、3 被累加成 6 |
| 欢迎 | 入场通知可能抽样或不可见；不能把发言、在线列表首次出现一律当成刚入场；重复进入需要冷却 |
| 粉丝团升级 | 优先明确升级事件；加入粉丝团不等于升级；首次读取等级只建立基线 |
| 荣誉/财富升级 | 可能只能从其他互动携带的等级推断；只能说观察到等级变化，不能声称捕获所有实际升级 |
| 文字发送 | 控件可能受控于前端框架；脚本提交不保证平台接受；需要处理限频、静音、验证码和账号权限变化 |

礼物、升级、欢迎分别配置冷却和消息优先级；所有文字共享房间发送预算，欢迎可批量合并。具体预算以目标账号实测及平台约束确定，不把某个固定频率当作安全承诺。账号异常、目标身份变化或连续发送失败时暂停自动发送。

## 实施顺序与验收

1. **能力探针**：在三种目标环境分别记录事件样本、字段、采样/遗漏和当前账号的发送能力。用人工操作或已授权的一次发送验证实际回执；仅 DOM 输入成功不算通过。
2. **纯后端回放**：保存脱敏事件样本，用规则与模板生成动作但不发送。测试连击、重复/乱序事件、等级基线、换房、断线和消息积压。
3. **单房间闭环**：先选择探针通过的环境实现礼物感谢和有限欢迎；发送开关、停止指令和日志通过 CLI/TOML 提供，UI 开发保持暂停。
4. **扩展事件与平台**：加入两类升级，接入第二平台，最后补齐微信客户端，能力缺失必须显式显示为未支持而不是猜测触发。
5. **可选智能能力**：在稳定事件和执行链路上加入话术改写、直播语境和知识库回复，保留规则兜底及发送审核策略。

在环境和样本未验证前不做两平台完整功能的工期承诺。验收重点：不跨房发送、不因断线重复发送、连击计数正确、等级不误报、限流和停止有效、失败有可解释记录。录像保持独立运行，并可利用事件时间线为后续精彩片段标记提供基础。

## 官方能力复核与主播/助播模式

2026-10-12 再次核查。用户确认尚无互动插件/直播小玩法应用或获批互动数据权限。

### 抖音：已确认的官方路线

1. **互动工具，小程序形态（抖音 App + 直播伴侣）**：官方明确提供 `tt.subscribeLiveInteractPluginMessage` 和 `tt.onReceiveLiveInteractPluginMessage`，可按获批权限监听 `live_like / live_comment / live_gift / live_follow / live_fansclub`。粉丝团变更有升级原因字段；粉丝团等级和荣誉等级值需要对应额外权限。此 API 在官方插件运行环境中使用，不是普通浏览器页面或 Rust 直接调用的通用 API。[官方 App + 伴侣指南](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/development/tutorial/app-interaction-guide)。
2. **互动工具，Windows 直播伴侣原生插件形态**：官方提供 PipeSDK 通信模型，订阅 `OPEN_LIVE_DATA` 获得互动数据。`SendMessage` 是插件与伴侣的 IPC 请求方法，不是向直播评论区发言的方法。[官方伴侣原生指南](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/development/tutorial/live-tool-guide)。
3. **直播小玩法服务端推送**：不同产品路线，需应用获批、对应数据权限及直播间正在挂载该小玩法。数据通过签名 HTTP 回调送到开发者服务端；不能仅凭主播账号登录或 Cookie 获取任意直播间的数据。评论范围也不能与互动工具文档的全量评论能力混为一谈。[官方数据开放说明](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/develop/server/live-room-scope/data-open/data-open-desc)、[评论互动能力](https://developer.open-douyin.com/docs/resource/zh-CN/interaction/jierushuoming/hudongshuju/pinglunshuju)。

当前互动工具接入页仍写明“插件业务更新中，暂不准入新插件”。文档保留了开发者入驻、提交提案、审核、主播使用插件的流程，但文档存在不代表当前新应用获批可行。主播身份或授权也不替代开发者应用准入。[官方接入指南](https://partner.open-douyin.com/docs/resource/zh-CN/live-interactive-tools/introduction/interactive-tools-guide)。

在上述互动工具公开 API 列表中未确认通用 `send_chat` / 直播评论发送接口；`x.publishEvent` 和小程序卡片通信也不能解释为向观众评论区发言。文档确认的是互动数据接收和上屏素材等能力，不足以确认纯官方自动文字感谢闭环。欢迎所需的完整入场事件及独立荣誉升级事件也尚未确认。

另有官方“抖音 SDK -直播接入说明”，列出第三方 App 观看直播、用户评论互动等能力，但该页说明直播接入仅 Android、SDK 及正式文档由技术支持提供，并限定数据使用于 SDK 合作目的。这条路线不等同于桌面主播场控的公开发送接口，需专项合作确认。[官方直播 SDK 说明](https://partner.open-douyin.com/docs/resource/zh-CN/dop/ability/douyin-live-sdk/douyin-live-sdk/interface-and-function)。

互动工具接入页还列出不连接网络、不经过开发者服务器的边界描述。因此该路线的数据向外部控制端或云端 AI 转发是否允许，需向官方确认；不能直接套用另一产品的服务端推送权限。原生方案可优先考虑在获批插件进程中运行 Rust 规则核心，外部联动另行核验。

### 视频号：本轮仍未确认

没有获得足以确认实时礼物、入场、等级事件及自动文字发送的公开官方接口证据。微信官方文档在网页检索读取时失败，进一步浏览器读取又被站点安全策略阻止，未通过替代浏览器或绕过方式访问。此限制仅说明本次未能完成官方页面核实，不能据此断言视频号不存在合作能力。

视频号助手或微信客户端本身能看到、操作相关功能，并不证明第三方开发者有对应开放 API；原站内部请求也不应标为官方开放接口。

### 四种模式的规划

| 产品模式 | 事件来源 | 文字执行 | 当前结论 |
| --- | --- | --- | --- |
| 抖音主播 | 获批官方插件/数据能力 | 官方发送能力待确认 | 预留；用户无既有准入权限，新插件准入暂停，无法立即验证纯官方闭环 |
| 抖音助播 | 已授权账号的页面脚本 | 当前登录助播账号在页面发送 | 可做能力探针；完整事件覆盖和发送确认尚需验证 |
| 视频号主播 | 预留官方适配器 | 预留官方执行器 | 官方事件/发送接口及准入均未确认，暂不能承诺实现 |
| 视频号助播 | 浏览器或微信客户端的独立适配脚本 | 对应已授权账号的可用发言入口 | 可做能力探针，浏览器与微信客户端分别验收 |

产品角色与接入方式独立建模：`role = host | assistant`，`event_source = official | page_script`，`action_executor = official | page_script`。这允许未来经用户明确选择后组合“官方采集 + 页面发送”，但组合模式必须标识为混合接入。用户要求的纯官方主播模式如果缺少发送能力，应报告未支持，不能静默退回注入脚本。

四种产品模式共用事件格式、规则、模板、队列和日志，不各自开发四套决策引擎。官方和脚本的能力采用显式清单，如礼物、粉丝团升级、荣誉等级快照、入场、文字发送和发送确认，未获批或未验证的能力保持禁用。

下一步建议：先取得抖音官方对以下问题的明确答复，再决定主播路线工期；同时保留两平台助播探针的独立推进路径。此次未联系平台、未创建应用、未编写或执行发言脚本，UI 开发继续暂停。

可提交给官方的核实问题：

- 当前是否接收新的感谢、欢迎、升级提醒类互动工具提案？有哪些主体和应用资质要求？
- 是否开放以主播或授权助播身份发送直播间文字评论的 API？具体文档、权限、运行端及限频是什么？
- 是否支持观众入场、粉丝团升级和荣誉等级升级事件？是全量事件、抽样事件还是等级快照？
- 官方互动数据能否进入本地 Rust 控制端，是否允许云端模型处理？
- Windows 伴侣插件、小程序插件和当前 macOS 场景分别有哪些可用范围？
