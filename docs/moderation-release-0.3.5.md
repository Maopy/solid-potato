# 0.3.5 按用户 ID 定制感谢昵称

新增抖音、视频号共用的 YAML 昵称映射表。礼物感谢中的 `{nickname}` 优先使用匹配到的专属称呼，未配置时沿用平台昵称。匹配依据是当前平台的完整用户 ID，与遮罩昵称无关；原始用户 ID、平台昵称、礼物去重、5 秒合并和发送回显匹配保持原样。

## 共享表

新包的房间配置已经引用 `config/nickname-mapping.yml`。将对应平台的空映射 `{}` 替换为自己的用户 ID 和昵称，例如：

```yaml
version: 1
platforms:
  douyin:
    '请替换为完整抖音用户ID': '霸气哥'
  wechat_channels:
    '请替换为完整视频号用户ID': '排面姐'
```

两个平台各自匹配，ID 相同也不会串用昵称。同平台多个直播间可以共用一份表；礼物感谢会使用相应称呼，比如“霸气！感谢霸气哥送来的玫瑰”。ID 必须加引号保留为完整字符串，不填昵称、房间号或礼物接收目标 ID。

旧配置需在房间 YAML 顶层增加：

```yaml
nickname_mapping:
  file: nickname-mapping.yml
```

相对路径以**房间 YAML 所在目录**为准，不是终端当前目录或控制总配置目录，也支持绝对路径。将新表复制到对应位置；不要覆盖自己的旧配置和数据。

## 房间专属覆盖

可在房间配置中补充或覆盖个别用户，不引用外部表也可以只使用 users：

```yaml
nickname_mapping:
  file: nickname-mapping.yml
  users:
    '请替换为完整用户ID': '本房间专属称呼'
```

优先级：房间 users > 共享表的当前平台条目 > 原平台昵称。没有 nickname_mapping 的旧配置继续使用原有行为。

专属称呼支持 1–32 个 Unicode 字符，会去掉两端空白，拒绝空白昵称、换行和控制字符。完整用户 ID 最长 256 个字符，不能带两端空白；兼容视频号 148 字符用户 ID。每个平台最多一万条配置，外部表最多 1 MiB，启动前检查文件与映射，失败时不会启动代理或创建日志目录。

映射只替换礼物感谢模板中的昵称，包括固定模板、按价值随机文案，以及包含 `{nickname}` 的超长礼物备用模板；不会改写欢迎或升级规则。若备用模板本身不包含昵称，仍按该模板输出。昵称值是普通文字，其中的花括号不会再次当模板执行。专属昵称不会套用原平台昵称的 12 字截断，但最终文案仍受既有总长度限制。

## 查找用户 ID

用户 ID 可在本地 `moderation-probe.sqlite3` 的 `probe_events.event_json` 中查到：礼物事件的 `user_id` 是送礼用户，`payload.recipient_user_id` 是收礼目标，二者不要混淆。视频号使用 native username，抖音使用完整十进制用户 ID；不要用“陌**”这类展示昵称作为键。

修改映射后需要重启场控并重新打开直播页；当前不热更新，不自动改写已经生成的草稿。映射表只在本地读取，不会整份注入平台页面，发送文字中仅体现实际命中的称呼。

## 验收

仅运行集成测试，不发送真实直播间消息。覆盖共享表的相对路径与平台隔离、房间覆盖、非法文件与昵称预检、32 字完整称呼、视频号 148 字符 ID、同名不同 ID 未误匹配、原始身份留存、两平台价格/随机文案与填入链路、回执重试文案不变，以及原有多房间与延迟回显恢复。
